# Front end ↔ OurSport API gap report
Front-end commit: none (`frontend`, `mock_backend` and `backend` are not git repositories) · Contract date: 2026-10-24

**What was compared**

- **Front end:** every function in `frontend/src/api/client.js` (117), the hooks in `src/api/` and `src/live/`, the scorer offline queue (`src/areas/scorer/`), `vite.config.js` and the screens under `src/areas/`.
- **Mock backend** (`mock_backend/`, "OurSport AI API" 0.1.0): the API the front end was built against. Its OpenAPI was generated by importing `app.main` (no server started): 118 HTTP operations + 1 WebSocket, 189 schemas. Field names and types below come from that contract and from `mock_backend/app/models.py`.
- **Real backend:** `gap_analysis/openapi.json` (67 operations, 96 schemas), with `backend/app` checked for the WebSocket envelope, the timeline event shape, error codes and CSRF.

No code was changed.

## Summary

**The front end and the mock agree with each other.** All 117 client functions have a matching mock route, and the field names the screens read match the mock's models. The gap is between **the mock and the real backend**: they are two different API designs.

| Aspect | Mock (what the front end expects) | Real backend |
| --- | --- | --- |
| Base path | `/api/...` for fan calls, no prefix for portal, publisher, editor and scorer calls | `/api/v1/...` everywhere |
| Field names | camelCase (`ApiModel` with `alias_generator=to_camel`, `models.py:7-10`) | snake_case |
| IDs | slugs (`"tarmo"`, `"olsu17"`) | UUIDs |

**The five most important problems**

1. **The front end sends no CSRF token and never refreshes the session, and the mock never required either.** Against the real backend every POST, PATCH and DELETE gets 403, and users are signed out after 15 minutes. Sign-in itself also can't work: the mock has password login, reset and demo login, while the backend has only magic links, and the front end has no page that reads the link token (D1, D2, A5–A7, A38).
2. **The data format is different everywhere.** The base path, camelCase vs snake_case, slug vs UUID ids, epoch ms vs ISO strings, and the score array vs an object differ on every endpoint. The cheapest fix is one adapter layer in `client.js` that maps backend responses to the shapes the screens already use (A1–A4, A23–A25).
3. **Match lists come from an SSE stream the backend doesn't have.** `App.jsx:24` → `useLiveFeed` → `/api/feed/stream` (mock `main.py:1400`) feeds every match list, fixtures tab, team page and live view. The backend's replacement is `getLive` / `getSchedule` per tournament plus the tournament WebSocket.
4. **Scoring is a different model.** The mock uses a signed-in scorer role, a `device` + `clientSeq` scheme, cricket-capable event definitions (`wicket`, `ball`, `pad: batting`) and returns the full `ScoringState` after every event. The backend uses QR scorer passes, `client_seq` per match, `string[]` event types, `EventAccepted` deltas, undo by server `seq`, and an explicit `startMatch` call (A30–A37, D4).
5. **The organiser flow doesn't fit the backend's automatic setup.** The mock's publisher wizard (`POST /tournaments`, teams, import, rulebook, rules confirm) and club portal have no counterpart. The backend's headline features have no UI: automatic setup, match-day console, rescheduling and scorer passes (F4, F5, F7–F9; section C).

3. **Notifications.** The mock pages notifications (`cursor`, `limit`, `nextCursor`), returns `unreadCount`, and gives each item a `title`, `body` and deep `link`. The backend returns a flat list with `text` and `team_id`. Is pagination planned, and can items carry a link target (match or tournament id)?

7. **Standings.** Can rows carry qualification status (through/out/alive), and the page the number of qualifying places and a tiebreak label and description (mock `qualifyCount`, `tiebreak`, `status`)? Top scorers: planned, or deliberately left out?
8. **Scenarios.** `openapi.json` says `getScenarios` returns `ScenarioPage[]`, the README says `ScenarioPage`. Which is right? Can `scenario` get a schema (headline, detail, position, points, max points, remaining fixtures, status), like mock `ScenarioCard`?

Which of these map to `getComparison` / `getMatchAnalysis` / `getScenarios`, and is a live "if it ends like this" line planned?
10. **Team identity.** Badges everywhere use the team's `short` code and `color` (and club colours). Is any team branding planned on `TeamName`/`TeamPage`?
11. **Scorer screens.** `ScorerMatch` has only team ids, with no names, pitch or competition, and there's no scorer-state read (score, period, events with server `seq` for undo, rosters). Can `getMatch` and `getTimeline` be called with `Authorization: Pass`? Will `getEventTypes` get a richer definition (labels, which side or player each type takes, what changes the score), or should the front end hard-code football?

## Resolution (2026-10-24, T-066)

Decision: **the backend's conventions are the contract** (`/api/v1`, snake_case, UUIDs, ISO 8601 UTC,
problem+json, magic links, QR scorer passes, AI setup). The backend gained what the screens need; the mock now
serves the same contract; the front end calls it and adapts responses to its screen shapes in one place.
